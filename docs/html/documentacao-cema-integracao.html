1. O que ele está apresentando

CompozyOS = um “sistema operacional” local-first para trabalho com agentes de IA.

A tese central (e o que a live vende):

Qualquer um consegue promptar um agente. Fazer agentes trabalharem de forma contínua ainda é engenharia: loops, triggers, cron, memória, permissões, approvals, observabilidade e cola entre ferramentas. O CompozyOS transforma esse stack inteiro em um produto.

Em vez de você montar scripts + MCP + filas + memória à mão, o daemon local vira a fonte da verdade: sessions, tasks, loops, memory, permissions, automation e tools.

Fontes: compozy.com · github.com/compozy/compozy

Conceitos-chave

  1. Daemon dono do estado — fechar o terminal não mata o trabalho; session é durável.
  2. Tasks com claim/lease — fila compartilhada humano↔️agente; heartbeat; sem double-execution.
  3. Memory ≠ vector DB — arquivos Markdown tipados (user, feedback, project, reference) + “dream consolidation”.
  4. Skills / hooks / extensions — contratos em arquivo (SKILL.md, TOML hooks), não plugin spaghetti.
  5. Compozy Network — peers Live trocam greet/whois/say/capability/receipt/trace.
  6. Bridges — Slack, Discord, Telegram, WhatsApp, Teams, GitHub, Linear… webhook → session.

1 — Planejamento Crawler Superlógica

Escolha de tecnologia, MFA, arquitetura alvo e riscos. Fonte original: planejamento-crawler-superlogica.html

1. Qual problema estamos resolvendo?

Hoje o repositório já extrai cobranças, contratos e taxa adm via API REST (app_token + access_token). Um crawler só se justifica quando a API não entrega o relatório, a tela ou o export que o negócio precisa.

Já resolvido sem crawler /cobrancas, /contratos, /repasses → Google Sheets (Apps Script em produção).
Candidatos a crawler Relatórios só na UI, export XLSX/PDF sem endpoint, fluxos de aprovação em tela, ou dados que a API lista de forma incompleta.
Antes de escolher ferramenta: listar quais telas/relatórios faltam. Sem esse inventário, a decisão de stack fica especulativa. Relatórios de frota/OS (placa, CELESC) em docs/pdf/*.xlsx parecem de outro sistema — confirmar se entram no escopo Superlógica.

Experiência citada: Puppeteer, Cypress, Robot Framework. Incluímos Playwright (sucessor natural do Puppeteer no ecossistema Node).

4. Recomendação (MFA via e-mail alternativo)

MFA continua presente, mas o código/token chega em um e-mail alternativo controlado pelo time. O crawler lê essa inbox, extrai o OTP e completa o login — viabilizando job não-atendido.

Confirmado: login tem MFA · Estratégia: inbox alternativa recebe a geração do token/OTP · crawler (Playwright + leitor IMAP/API de e-mail) automatiza o desafio. Tokens de API (app_token / access_token) seguem preferíveis quando o dado já existir na API — o crawler cobre o que a API não entrega.
Dado na API? Continuar com tokens oficiais (Apps Script / Node). Sem browser.
Dado só na UI? Playwright: login → poll e-mail OTP → preencher MFA → export/DOM. Job pode rodar em cron.
Ferramenta Playwright (1ª) ou Puppeteer (alternativa). Cypress/Robot: não.

Peças do fluxo MFA por e-mail

PassoO que faz
1. Browser Abre Superlógica, preenche usuário/senha, dispara envio do MFA
2. Inbox Poll IMAP (ou Gmail API) na caixa alternativa; filtra remetente/assunto; regex no corpo para extrair o código/token
3. MFA Cola o OTP na tela e conclui o login
4. Sessão Persiste storageState para reuso até expirar (evita MFA a cada run)
5. Extração Navega, exporta XLSX/CSV ou lê DOM; grava Sheets/arquivo

O que não recomendamos

  • Cypress — runner de teste; IMAP + OTP + cron ficam tortos.
  • Robot Framework — só se o time for Python-first; aqui rumo Node/TS.
  • Usar e-mail pessoal de alguém — inbox deve ser dedicada (conta de serviço / alias).
  • Duplicar na UI o que já sai de /cobrancas, /repasses, etc.
Pasta alvo: integrations/superlogica-crawler/ (Node + TypeScript + Playwright + cliente IMAP/Gmail).

6. Riscos específicos do Superlógica

Pontos que mudam a avaliação custo × benefício do crawler.

  • Login com MFA — confirmado — automatizado via e-mail alternativo (poll OTP). Risco: atraso/entrega do e-mail, mudança de template, bloqueio de IMAP.
  • Segurança da inbox — conta dedicada, senha de app / OAuth, sem compartilhar e-mail pessoal; OTP não deve ir para logs permanentes.
  • SPA e seletores — mudanças de front quebram scripts; exports e XHR quebram menos.
  • Rate limit / sessão — reusar storageState para não disparar MFA a cada execução.
  • Compliance — automação de UI + leitura de e-mail; tokens oficiais de API seguem preferíveis quando existirem.
  • Duplicidade — não reimplementar em crawler o que o Apps Script já cobre via API.

Como o script monta a aba Taxa Adm Realizada.

Contratos ativos e inativos

2. Objetivo

Automatizar o fluxo financeiro entre os dois sistemas, sem substituir as automações de planilha atuais.

Fluxo principal — Cobrança

  1. Ler no Superlógica as despesas/parcelas de contrato (aluguel e compra).
  2. Criar no Controlle um lançamento de entrada.
  3. Incluir o número do contrato na descrição (Contrato {n}).
  4. Guardar o vínculo (id despesa ↔ id lançamento) para não duplicar.

Retorno opcional — Pagamento

  1. Listar entradas pagas no Controlle com número de contrato.
  2. Localizar a despesa/parcela no Superlógica.
  3. Liquidar no Superlógica e marcar o pagamento como processado.

6. Regras de negócio

  1. Só sincroniza registros com número de contrato válido.
  2. Não recria no Controlle se a despesa Superlógica já foi sincronizada.
  3. No retorno opcional: não reliquida se o pagamento Controlle já foi processado.
  4. Locação e compra usam categorias diferentes no Controlle.
  5. Em erro parcial: registrar falha, seguir o lote, resumir no final.
